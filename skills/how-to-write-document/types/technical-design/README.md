# 技术方案 / 设计文档写作规范

## 一、整体要求与约束

- **用途（必须）**：说明工程问题、方案取舍、系统行为和交付路径，使评审者能判断可行性、实施者能执行、验证者能核验、运维者能识别故障并恢复。跨组件、接口、数据或运行风险较大的改动应形成完整设计；局部小改动可按风险缩减内容，但不能省略相关影响与验证。
- **读者（必须）**：面向研发、架构、安全、测试、运维及受影响的系统维护者。交代系统边界和术语，不能假定读者参加过讨论；正文突出评审所需结论，协议细目和原始实验记录可放附录。
- **证据（必须）**：区分已观测事实、估算、假设和待验证判断。现状、性能、成本与故障结论应附来源、采样时间/窗口、环境及口径；估算给公式、输入依据和不确定性。不得把目标当成已实现效果，不得使用无来源的精确数字。
- **篇幅与取舍（必须）**：以可评审、可实施、可验证为准，不以固定页数替代质量。保留影响决策、实现正确性和恢复安全的信息；重复背景、逐字讨论记录和过长代码移至附录。条件不适用的部分保留标题并说明原因，不能空白跳过。
- **风格（必须）**：客观工程化，事实、建议与决策分开；使用“在什么条件下，由哪个组件执行什么动作，得到什么结果”的表达。首次解释缩写，单位和术语统一；禁用“显著提升”“安全可靠”等无证据判断。**建议**用组件图、时序图、状态表和前后对照表达复杂关系，但图必须配文字说明。
- **缺失信息（必须）**：未知负责人、日期、基线、阈值、预算、外部承诺统一标“待确认”，注明影响、确认路径和阻塞范围；确认人或期限也未知时继续标待确认，不虚构姓名或时间。缺失关键证据时给验证计划，而不是补出结论。关键未决项未关闭前不得将方案标为已批准或可上线。
- **规范强度**：“必须”为交付底线；“建议”可按场景调整并保留理由；“条件适用”须判断触发条件，不适用时说明原因。产品行为背景可链接 [PRD](../prd/README.md)，决策摘要可链接 [One Pager](../one-pager/README.md)，此处不承载它们的写作约束。

## 二、整体结构与模板

章节按下列顺序组织，顺序固定；不适用的小节说明原因后省略，不删除整段证据链。

1. 文档信息
2. 摘要与评审请求
3. 背景与现状
4. 目标、非目标与约束
5. 备选方案与决策
6. 详细设计
7. 风险、依赖与未决问题
8. 验证、上线与回滚
9. 实施计划与分工
10. 附录与来源

完整可复制模板见 [templates/technical-design.md](templates/technical-design.md)，内含空白模板、填写示例、真实示例链接。写作时先取模板，再回到本文「三、各部分写作要求」逐节核对；模板与本文小节一一对应。

## 三、各部分写作要求

### 1. 文档信息

- **目的**：让读者辨认当前有效版本、评审状态和材料来源。
- **必须写什么**：标题、状态、版本与变更摘要、作者及评审方、更新日期、相关材料；未知字段显式待确认。批准状态必须能追溯到实际评审记录，重要范围变更必须留痕。
- **表达要求**：短列表即可；区分作者、评审者和实施责任方，不把被提及的人当作已承诺负责人。
- **如何检查**：标题与实际改动一致，版本和状态不冲突，来源可定位；变更摘要指出影响了哪些设计结论。
- **常见错误**：预填发布日期或审批人；链接旧版本却不说明；草案显示为已定稿。

### 2. 摘要与评审请求

- **目的**：让评审者先知道要解决什么、建议如何解决、需要决定什么。
- **必须写什么**：工程问题、推荐方案、关键判据、主要代价与风险、本次请求；结论未定时写候选项及需要的验证。
- **表达要求**：压缩为短段或列表，先结论后依据；请求具体到方案选择、约束确认或资源边界，避免复述目录。
- **如何检查**：摘要中的结论能在后文找到证据；读完能复述建议和最重要的取舍。
- **常见错误**：只讲背景；隐去迁移代价；把倾向写成已批准决定。

### 3. 背景与现状

- **目的**：建立问题事实和现有系统模型，防止针对错误根因设计。
- **必须写什么**：受影响组件与边界、当前调用/数据链路、问题发生条件、影响对象、证据口径、不处理的后果；根因已证实还是推测须说明。
- **表达要求**：图标出外部依赖和信任边界，文字说明关键路径；数据注明环境、单位、采样范围与时间，避免混用线上和实验结果。
- **如何检查**：证据能支持问题陈述；能区分症状、根因与约束；历史背景均与本次决策有关。
- **常见错误**：用单次日志推断整体容量；架构图只有组件名没有流向；把未经验证的瓶颈当事实。

### 4. 目标、非目标与约束

- **目的**：明确成功条件、工作边界和不可违背的限制。
- **必须写什么**：带编号的目标、可观测基线与目标条件、验证方法；非目标及与目标的交界；约束来源与确认状态。尚无基线时写测量计划，不编目标值。
- **表达要求**：目标描述结果而非动作；指标给单位、统计口径、负载与窗口。硬约束与偏好分开，条件适用的约束说明触发场景。
- **如何检查**：每个目标能映射到第 8 节验证；非目标不与详细设计冲突；约束有真实来源。
- **常见错误**：“完成重构”作为唯一目标；非目标留空；把未经确认的截止日期作为硬限制。

### 5. 备选方案与决策

- **目的**：保留选择依据与被放弃的路径，便于复评。
- **必须写什么**：比较判据、可行候选、同口径的收益/代价/风险、推荐理由与淘汰理由。**条件适用**：“维持现状”若可行，应纳入比较；若只有一个可行方案，解释其他路径为何不可行，不凑数量。
- **表达要求**：先给硬门槛，再给排序偏好；估算不混同测量。没有验证的比较写不确定性和验证动作。
- **如何检查**：推荐方案符合硬门槛；结论能由判据推导；关键假设变化有重新评估条件。
- **常见错误**：“综合考虑选用”而无判据；为衬托推荐方案制造明显不可行候选；不同负载下比较时延。

### 6. 详细设计

- **目的**：把选择落实为可实现、可联调、可运行的系统行为。
- **必须写什么**：以下各设计面均须判断适用性；适用时写到实施者不必重新猜测契约和失败语义的程度，不适用时写原因。
- **表达要求**：职责、条件、动作与结果明确；**建议**用图表与短代码片段辅助，代码必须标明是否可执行及适用环境。
- **如何检查**：正常与失败路径闭合，边界一致，设计能覆盖目标和约束，跨组件行为不存在责任空档。
- **常见错误**：只有架构图；实现细节堆砌却缺契约；默认所有依赖均成功。

#### 架构与关键流程

**必须**写组件职责、输入输出、同步/异步边界、调用顺序、状态迁移和一致性要求；流程图标出分支与终态。**建议**说明关键不变量及其维护位置。检查是否能从入口追到结果、状态由谁写入、并发下是否成立；避免箭头没有语义或图文命名不一致。

#### 接口与协议

**条件适用：新增或修改接口时必须**给调用方、协议/版本、请求响应字段、类型、必填性、默认值、错误语义、鉴权、超时与幂等契约；修改接口给前后对照。示意载荷用占位符，若使用具体值必须标“虚构格式示例”。检查调用方与服务方是否能据此独立实现、重复请求是否安全；避免“新增字段”而无类型和旧端行为。

#### 数据模型、生命周期与迁移

**条件适用：涉及持久化或数据变更时必须**写字段/约束/索引、读写权属、保留与删除、变更前后模型、迁移顺序、校验、并发写入处理、失败恢复。说明备份、回填、切换、回滚的可逆边界；不可逆变更须说明数据损失风险、补偿或前向恢复及审批前置条件，不能声称总能回滚。检查迁移和恢复能否在目标环境演练、旧代码是否能读取新数据；避免仅回滚代码、不处理数据。

#### 异常、超时与恢复

**必须**覆盖关键依赖失败、超时、重试耗尽、部分成功、重复/乱序请求及并发冲突中适用的情况；写检测信号、错误传播、重试上限/退避、降级结果、补偿、告警与恢复条件。检查重试是否放大负载、部分成功是否可收敛、状态是否可重复恢复；避免无限重试或吞掉错误。

#### 兼容与演进

**条件适用：存在旧客户端、滚动部署、历史数据或外部调用方时必须**写兼容矩阵、版本混用行为、发布顺序、特性开关、废弃条件及沟通依赖。检查新旧组件共存和回退路径；避免把“兼容”当未定义承诺、先删字段后迁移调用方。

#### 容量、性能与成本

**条件适用：涉及负载、资源或性能目标时必须**写流量/数据量假设、峰值和增长依据、资源估算公式、时延预算、瓶颈、限流与容量边界；成本区分一次性投入与持续运行。无数据时给测量/压测计划和决策限制。检查输入与单位可复算、平均值未替代峰值、估算有验证；避免伪造吞吐数字或遗漏存储、网络等主要成本。

#### 安全、隐私与审计

**必须**判断身份认证、授权边界、敏感数据、攻击面与审计需求；涉及时写最小权限、凭据管理、传输/存储保护、脱敏、保留/删除与异常访问处置，合规依据须可追溯。检查跨边界访问是否授权、日志是否泄密、权限变更是否留痕；避免以“内网系统”为安全豁免或把未经评审的设计称为合规。

### 7. 风险、依赖与未决问题

- **目的**：暴露可能改变方案或阻止交付的条件。
- **必须写什么**：稳定编号、风险触发条件/依赖交付物/待决问题、影响、应对或确认路径、责任方、时间与状态；未知值待确认。区分期望时间与对方已确认承诺，并标出阻塞阶段。
- **表达要求**：风险写成“条件—影响—措施”，未决问题写成可回答的问题；无需无依据地填概率数字。
- **如何检查**：重大风险有检测和应对；依赖有完成条件；关键未决项未被设计正文悄悄视为已解决。
- **常见错误**：把风险写成口号；填了负责人却未确认；未决项没有说明不解决会阻塞什么。

### 8. 验证、上线与回滚

- **目的**：证明目标达成，并限制发布失败的影响。
- **必须写什么**：逐目标、关键风险的测试/实验与通过条件，验证环境及证据；上线前置检查、发布顺序、灰度对象/批次、观察信号和停止条件；回滚触发条件、执行角色、操作顺序、数据处理和恢复核验。未知阈值或执行方标待确认，并视其重要性阻塞上线。
- **表达要求**：区分开发验证、发布判定与运行监控；操作按顺序写，必要时链接操作细节。**条件适用**：无法灰度时解释原因和替代风险控制；无法回滚时给前向恢复及批准条件。
- **如何检查**：每个目标有验证方法，每个停止/回滚条件可观测，恢复覆盖代码、配置与数据且经过适当演练。
- **常见错误**：“测试通过后上线”；只有发布动作没有停止条件；回滚后不检查一致性。

### 9. 实施计划与分工

- **目的**：把方案拆为有依赖、有产物、可跟踪的执行步骤。
- **必须写什么**：阶段工作、交付物、前置依赖、责任方、时间或估算依据、完成条件；包含联调、验证、迁移和运行准备等适用工作。
- **表达要求**：已承诺排期与初步估算分开；没有负责人或日期则待确认，不为了填表制造承诺。**建议**按可独立验证的阶段拆解。
- **如何检查**：阶段顺序符合依赖，完成条件可核验，计划覆盖全部设计改动与恢复准备。
- **常见错误**：只排开发不排验证；多人共同负责却无人确认交付；估算精确到日期但无依据。

### 10. 附录与来源

- **目的**：提供可追溯证据与实现细节，不拖慢正文评审。
- **必须写什么**：正文引用的来源索引、适用版本/时间和用途；适用时收录实验配置、计算过程、协议细目与历史决策。
- **表达要求**：正文先写结论，再链接支持材料；附件不能代替关键决策、接口契约或恢复结论。敏感信息使用有权限控制的来源，不贴凭据或生产个人数据。
- **如何检查**：链接可解析且目标正确，引用足以定位证据，附件与正文版本一致。
- **常见错误**：只有链接没有说明；原始聊天记录代替设计结论；正文藏在附录里。

## 四、交付前检查

- [ ] 文档按模板编号排列，头部信息和每个部分都有内容或不适用理由；批准状态有依据。
- [ ] 问题、根因判断、目标、方案选择和验证形成可追溯链条；事实、估算、假设清晰区分。
- [ ] 比较口径一致，推荐理由明确，关键取舍和不确定性未隐藏。
- [ ] 接口、数据、异常、兼容、容量、安全均完成适用性判断；适用项达到可实施粒度。
- [ ] 发布、停止、回滚或前向恢复可操作，数据可逆性和恢复验证已说明。
- [ ] 负责人、日期、指标、预算与外部承诺均有依据；未知项标待确认并注明阻塞影响。
- [ ] 图、术语、字段、单位与状态一致；Markdown 围栏成对、表格可读、链接有效且无敏感泄露。
- [ ] 删除无依据形容词和重复材料，未用篇幅达标代替工程完整性。
