# 优化策略手册

## 1. 基本模型

这是一个**有预算的黑盒优化**，而且一次 prompt 要同时服务多个目标模型：

```text
system prompt ──┬─→ 目标模型 A（endpoint/key/temperature…）─→ 输出 ─┐
                ├─→ 目标模型 B（独立配置）──────────────→ 输出 ─┼─→ rubric 判分 ─→ 模型分 ─→ 加权总分
                └─→ 目标模型 N …────────────────────────→ 输出 ─┘
```

每次评测都有成本，分数还有噪声；模型越多，成本按模型数线性增长。策略不是「让模型自由发挥重写」，而是：

1. 在**优化集（search）**上，对每个目标模型分别测量当前 prompt；
2. 把所有模型的失败样本（模型名、输入、输出、失败准则与理由）交给优化模型；
3. 生成若干**完整替换 system 消息**的候选，而不是零散补丁；
4. 在 search 上实测候选，按**模型加权总分**只保留严格更好的；
5. 对最终版本在**全量数据**上重算，和基线做同口径比较，并逐个模型看变化。

实现是贪心爬山 + 停滞早停（`--patience`），每轮从当前最优出发。优点是调用可控、结果可解释；代价是可能错过需要先退一步的改动。

## 2. 候选应该改什么

优化模型的提示词要求「针对不同失败模式生成不同候选」。人工审查时，好的候选通常属于以下几类：

| 策略 | 适用失败 | 示例改法 |
| --- | --- | --- |
| 输出契约 | 格式、字段、顺序不稳定 | 明确要求先给结论，再给三条以内的依据 |
| 必需要素清单 | 漏掉渠道/步骤/来源 | 把「必须包含 X、Y」写成检查清单 |
| 证据约束 | 编造事实、引用不存在的链接 | 要求只使用给定材料；不确定时明确说缺失 |
| 边界与拒答 | 越权承诺、超范围回答 | 规定不能承诺的内容与转人工条件 |
| 任务分解 | 多步任务只做第一步 | 要求按「判断 → 依据 → 下一步」组织 |
| 自检 | 明显错误、遗漏 | 要求在输出前核对 rubric 要求的要素（不暴露 rubric） |
| 压缩去噪 | prompt 太长、规则互相冲突 | 删掉无效规则，合并重复要求 |
| few-shot | 风格/格式难以描述 | 在固定消息中给示例（示例不得来自测试行；注意候选只改 system，不直接改 few-shot） |

多模型场景额外注意：

- 优先修**多个模型共同失败**的模式；只针对一个模型的特例容易让其他模型退步。
- 看每个模型的分差，而不是只看加权总分；权重高的模型会掩盖权重低模型的退化。
- 不同模型的失败理由可能互相矛盾（一个嫌太长、一个嫌太短）；这种情况应在 prompt 里给出可验收的边界，而不是折中成含糊表述。

不该做的：

- 把数据集行里的具体问题、答案、编号写进 prompt；
- 在 prompt 里提「rubric」「判分」「评测」「数据集」；
- 为了命中判分器的措辞而加固定开头词、固定长度；
- 把任务范围改小以规避难例；
- 堆砌「专业」「高质量」「详细」这类无法验收的词。

## 3. 预算怎么算

单轮成本（每对模型-行一次任务调用 + 一次判分调用）：

```text
每候选 = search_rows × 目标模型数 × (1 + 是否有 LLM 判分)
每轮   = 1 次候选生成 + candidates × 每候选
总计   ≈ baseline(search) + rounds × 每轮 + 全量重算(baseline + best)
```

示例：200 行、2 个目标模型、holdout 0.2（search 160）、3 轮、每轮 4 个候选、全部有 LLM 判分：

```text
baseline(search) = 160 × 2 × 2 = 640
每轮 = 1 + 4 × 160 × 2 × 2 = 2561
3 轮 = 7683
全量重算 = 2 × 200 × 2 × 2 = 1600
合计 ≈ 9923 次逻辑调用
```

这通常偏贵。压缩方式（按优先级）：

1. `--search-size 40`：候选只在 40 行上比，最终仍全量重算；
2. `--rounds 2`、`--candidates 3`；
3. 把客观准则改成 `check`，减少判分调用；
4. 减少目标模型数量或给不重要的模型更低权重（但不要为了省成本删掉用户要求的模型）；
5. 只在低分模型-行对上生成候选（工具已按最差对分析），但不能只评测低分对，否则分数不可比。

`--dry-run` 会按实际参数给出估算。**先估算，再让用户确认 `--max-calls`，再开始调用。**

## 4. 留出集与泛化

- `--holdout 0.2`：留 20% 行不参与候选生成与择优，只用于最终验证。
- 数据少于约 50 行时，留出集会让 search 太小，通常不设；此时报告必须写「样本内结果」。
- `--search-size` 是对 search 的再采样，不替代 holdout；最终报告仍覆盖全部行。
- 只有 holdout 也提升（且不是 1–2 分的噪声）时，才能说「在未见数据上更好」。
- 多模型时分别看每个模型的 holdout：某个模型在 search 上涨、holdout 不涨，说明该模型的提升可能来自过拟合或判分噪声；如果高权重模型出现这种情况，不要继续加轮次。
- 想更稳：换 `--seed` 重跑一轮优化，比较两次选出的 prompt 与 holdout 分数；差异大说明数据/判分噪声大。

## 5. 什么时候停

- 基线已 100：没有优化空间，先怀疑 rubric 太松。
- 连续 `--patience` 轮无提升：停止，接受当前最优。
- 预算接近上限：工具会在评测前检查并停止；剩余预算优先留给全量重算。
- 候选连续被安全校验丢弃（含 `{input}`、超长、重复）：检查优化模型是否在乱写，必要时换模型。
- 分数在涨但 holdout 不涨：大概率过拟合 search 或判分噪声，不要继续加轮次。
- 出现退步行且总分的提升集中在少数行：检查是否用通用规则换来了个例收益。

## 6. 诊断分数变化

打开 `report.md` 与 `results/*.jsonl`，按顺序看：

1. **总分**：基线 → 最优，是否超过噪声范围。
2. **逐模型分**：每个模型都涨/至少不显著退步，才算全面改善；加权总分涨但某模型大跌，要明确提示用户。
3. **search vs holdout**：两者同向才算泛化；holdout 明显更低说明过拟合。
4. **分准则**：提升来自真正重要的准则，还是来自容易刷的格式项。
5. **退步的模型-行对**：最优 prompt 是否让原本正确的对变差；退步多于提升时，即使平均分略高也应谨慎。
6. **失败理由**：判分 rationale 是否指出具体缺失，还是空泛的「不够好」。
7. **warnings**：样本内、跳过对、同模型判分、预算不足、全量评测不完整、候选泄漏拦截。

## 7. 反作弊审查清单

交付前逐条检查 `prompts/best.txt`：

- [ ] 没有出现数据集中的具体输入、答案、编号、人名、数字组合。
- [ ] 没有「rubric」「judge」「grader」「dataset」「evaluation」等字样。
- [ ] 没有固定开头词、固定长度、固定标点等只对判分器有利的规则。
- [ ] 没有把任务范围改小、拒答本应回答的问题。
- [ ] 没有编造政策、链接、电话、价格或承诺。
- [ ] 语言与用户要求一致；规则彼此不冲突。
- [ ] 每一条要求都能在输出中被验收。

发现任何一条不满足：丢弃该候选，重新生成或回到基线交付。

## 8. 结果怎么汇报

必须包含：

- 数据集路径、行数、search/holdout 行数、数据集 hash 前缀；
- 每个目标模型的 name、model、endpoint、权重、temperature、max_tokens（不含 key）；
- 判分/优化模型与 endpoint（不含 key）；
- 评分口径与公式；
- 基线总分、最优总分、差值、search 与 holdout 差值；
- **每个模型**的基线/最优/差值，以及主要退步的模型-行对；
- 分准则变化；
- 调用量、token、缓存命中与预算；
- 样本内/留出集的限制、判分偏差、随机性；
- 最优 prompt 文件路径与复现命令。

不要只贴一个「提升了 X 分」。没有口径、模型列表和限制的分数没有意义。
