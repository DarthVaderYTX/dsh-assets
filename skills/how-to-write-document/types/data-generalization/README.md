# 数据泛化规则写作规范

## 一、整体要求与约束

- **用途（必须）**：定义“把原始数据变成可共享、可对外、可用于评测或统计发布的形态”的规则，让使用方知道每个字段被改成了什么、还能做什么分析、不能推断什么。适用于对外数据交付、跨部门数据共享、评测集发布、日志开放与统计披露；不适用于权限、加密、访问控制本身（那属于[技术方案](../technical-design/README.md)的安全设计），也不适用于单纯的数据字典（无转换规则时用字段说明文档）。
- **读者（必须）**：数据使用方按字段字典理解口径与限制；开发按规则实现转换；合规与安全按目的、要求与证据审查；运营按示例核对边界情况。
- **可执行性（必须）**：每条规则必须能被执行——写清适用字段、输入、算法与参数、输出、边界与异常处理。只写“做脱敏处理”“模糊化”不算规则。
- **保真与可核查（必须）**：说明泛化后保留哪些统计特征（分布、趋势、排序、关联），以及因此损失了什么分析能力。示例必须来自真实数据或明确标注虚构；不得把虚构示例当作实际输出，也不得用示例代替规则。
- **一致性与可关联（必须）**：同一实体在不同表、不同文件中的泛化结果必须能按规则推导——要么保持可关联（同一映射表、同一盐值），要么明确声明不可关联及影响。字段名、单位、时区、枚举含义必须与上游系统一致。
- **缺失信息（必须）**：未定的阈值、盐值、审批状态、适用范围与生效日期标“待确认”，并说明对使用方的影响；不得为了显得完整而编造参数或阈值。
- **规范强度**：“必须”为交付底线；“建议”可按场景调整并保留理由；“条件适用”须判断触发条件，不适用时说明原因。

## 三、各部分写作要求

### 0. 文档信息

- **目的**：让使用方确认规则版本、适用范围与生效状态。
- **必须写什么**：文档名称与版本；适用的数据集、系统或交付物；责任方（数据Owner、安全/合规审阅人）；审批状态；生效日期与失效日期；变更记录；关联材料（数据字典、脱敏方案、交付合同条款）。
- **表达要求**：短字段列表或小表；版本号与生效日期分开，规则变更必须能追溯到版本。
- **如何检查**：读者能判断“我拿到的数据是否适用这份规则”；审批状态与生效状态不矛盾。
- **常见错误**：草案标成生效；只写“最新版”无版本号；生效日期晚于数据交付日期却未说明。

### 1. 泛化目的与适用范围

- **目的**：说明为什么泛化、泛化到什么程度，防止“为了安全全部抹掉”或“名为泛化实为原样输出”。
- **必须写什么**：目的（合规与隐私要求、对外共享、评测集发布、统计披露、降低重识别风险等）；要保护的客体（个人、账号、设备、商户、位置）；使用方与允许用途；覆盖范围（字段、数据源、环境、时间窗、数据量）；不覆盖的字段与原因；**非目标**（例如不做加密、不改变业务口径、不保证不可逆）。
- **表达要求**：目的与范围写成可检验的句子（“对外共享的分析表中不出现可定位到个人的精确坐标”），不用“提升安全性”这类口号。
- **如何检查**：每个泛化字段都能对应到某个目的；范围之外的字段有明确说明，不被误认为已处理。
- **常见错误**：目的写成“按公司要求”；范围只写“全部数据”；不说明使用方与用途限制。

### 2. 泛化要求与约束

- **目的**：给出规则必须满足的硬条件，供实现与审查判断。
- **必须写什么**：外部要求（法律法规、合同、行业标准、内部制度）及其条款位置；泛化强度与保真度要求（保留哪些分布、精度上限、分桶数、最小分组规模 k）；一致性与可关联性要求；可逆性要求（不可逆 / 可逆及密钥与授权方式）；性能与成本约束（吞吐、时延、存储）；格式与命名约束（字段类型、编码、单位、时区）；审计与留痕要求。
- **表达要求**：要求表（编号 / 要求 / 来源 / 验证方式）；区分“必须满足”与“尽量满足”。
- **如何检查**：每条要求能对应到第 4 节规则或第 6 节校验；要求之间不冲突，冲突时有优先级。
- **常见错误**：只写“符合隐私法规”不指条款；保真度没有量化；可逆规则不写密钥管理。

### 3. 数据字段定义与表述

- **目的**：让使用方在不看原始数据的情况下正确理解每个字段的含义、口径与限制。
- **必须写什么**：字段字典表——字段名（与上游一致）、业务含义、数据类型与格式、取值域或单位与时区、示例（原始值，必要时脱敏）、敏感级别、是否泛化、对应规则编号、泛化后示例、备注（口径、缺失值含义、枚举映射）。字段顺序与数据文件一致。
- **表达要求**：一张主表；枚举字段在表后给取值与含义对照；时间字段写清时区与精度；金额写清币种与单位；嵌套字段写路径（如 `device.os.version`）。
- **如何检查**：使用方按字典能写出正确的查询；泛化字段都能回指到第 4 节规则；同名不同义的字段已改名或注明。
- **常见错误**：字段名与上游不一致；只写类型不写口径；枚举值含义缺失；示例用真实个人信息。
- **禁忌**：以“见数据字典”代替本文表述；同一字段在表中与示例中描述不一致。

### 4. 泛化规则

- **目的**：把每个字段的转换写成可执行、可复核的规则。
- **必须写什么**：每条规则给编号、适用字段或类型、输入、转换方法（算法 + 参数 + 阈值 + 默认值）、输出、边界与异常处理、执行顺序与冲突处理、可逆性与密钥管理；“保持不变”的敏感字段也要显式登记为“原样输出及理由”。
- **表达要求**：规则表 + 必要的伪代码或正则；参数给默认值与设置依据；同一字段多条规则时说明优先级。
- **如何检查**：开发能按规则实现且无需再询问；边界输入（空值、超长、越界、异常格式）有明确输出；规则组合不产生歧义。
- **常见错误**：规则只写“哈希”不写算法与盐值；多个规则冲突无优先级；异常值直接丢弃且未声明。
- **禁忌**：把示例当规则；把参数写成“适当调整”。

### 5. 各类数据的例子及说明

- **目的**：用例子固定边界与预期输出，降低实现与验收的分歧。
- **必须写什么**：按数据类型给例子——数值（区间化、分桶、加噪、截断）、日期时间（截断到日/月/季、固定偏移、时区归一）、文本（掩码、替换、截断、分词）、枚举（上位类映射、合并稀有类）、标识符（哈希加盐、重编号、前后缀保留）、嵌套与数组（逐层规则、元素数量上限）、缺失与异常（保持缺失、统一填“未知”、非法值处理）。每个例子给：原始值 → 泛化值 → 说明；并覆盖边界样例（最小值、最大值、空值、超长、非法格式）。
- **表达要求**：按类型分表；示例值可为虚构但必须标注；真实示例须确认不含个人信息。
- **如何检查**：实现者能据此写出单元测试；同类型的新值能按例子类推；边界情况无遗漏。
- **常见错误**：只给正常值；示例与第 4 节规则矛盾；用真实手机号、身份证号作示例。

### 6. 校验、验收与审计

- **目的**：证明规则被正确执行，而不是只写在文档里。
- **必须写什么**：校验方法（人工抽样、正则与断言、泛化前后分布对比、关联一致性检查、回放测试）；抽样比例与样本量；验收标准（通过条件与失败处理）；审计留痕（谁在何时用哪个版本处理了哪批数据）；责任方与复核频率；发现偏差后的修复与重跑流程。
- **表达要求**：校验表（检查项 / 方法 / 样本 / 通过条件 / 工具）；给出可执行的校验脚本位置。
- **如何检查**：验收标准可自动判定；审计记录能定位到批次与版本；偏差有闭环处理。
- **常见错误**：只做一次性人工检查；验收标准写“无明显异常”；无审计记录。
- **禁忌**：用抽查通过代替全量校验而未说明风险；校验脚本与规则版本不一致。

### 7. 风险、例外与变更

- **目的**：说明规则的边界、例外审批与演进方式。
- **必须写什么**：风险（过度泛化导致数据不可用、残余可识别性、关联断裂、分布失真、规则漂移）；例外场景、审批人与记录方式；版本变更对下游的影响与迁移方式；废弃字段与规则的下线计划。
- **表达要求**：风险表（风险 / 影响 / 触发条件 / 缓解 / 责任方）；例外必须逐条登记，不写“特殊情况另行处理”。
- **如何检查**：主要风险有缓解或接受理由；例外有审批记录；版本变更通知到使用方。
- **常见错误**：只写“风险可控”；例外口头批准无记录；变更不通知下游导致口径错乱。

### 8. 附录与来源

- **目的**：保留实现与复核所需的完整材料。
- **必须写什么**：完整字段表（字段多时）、枚举映射表、正则与脚本、样例数据文件、制度与合同条款来源、术语表。
- **表达要求**：编号与正文引用一致；外部条款给版本与访问日期。
- **如何检查**：正文每条规则都能在附录找到实现或依据。
- **常见错误**：附录与正文版本不一致；只给截图无文本说明。

## 四、交付前检查

- [ ] 目的、使用方与适用范围明确；非目标与未覆盖字段已声明。
- [ ] 要求有来源与验证方式，保真度、可关联性与可逆性写清。
- [ ] 字段字典覆盖全部交付字段，命名、单位、时区、枚举与上游一致。
- [ ] 每条规则可执行：算法、参数、阈值、默认值、边界与异常处理齐全。
- [ ] 各类数据都有示例，且包含空值、越界、超长、非法格式等边界样例。
- [ ] 示例与规则一致；虚构示例已标注，未使用真实个人信息。
- [ ] 校验方法、验收标准、审计留痕与责任方明确。
- [ ] 风险、例外审批、版本变更与下游通知机制完整。
