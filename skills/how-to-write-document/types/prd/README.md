# PRD 写作规范

## 一、整体要求与约束

- **用途（必须）**：定义为谁解决什么问题、产品应表现为何种行为、做到什么程度可验收。作为需求评审、研发实现、测试验收与范围变更的共同规格，不用界面截图或实现任务清单代替产品规则。
- **读者（必须）**：面向产品、设计、研发、测试、数据及业务协作方。术语首次解释，需求独立可引用；让未参加讨论的人也能理解触发条件、规则和预期结果。
- **证据（必须）**：问题与场景应有反馈、研究、工单或数据依据，注明来源、时间/样本范围和局限。区分事实、假设、产品目标与预测收益；没有证据的场景标为待验证，不虚构典型用户。指标写清定义、基线、目标条件、统计口径及观察窗口。
- **篇幅与取舍（必须）**：以无歧义、可实现、可测试为准，不规定固定页数。正文保留范围、关键规则、状态、异常和验收；重复背景、长访谈及设计稿细目用附件承接。适用性必须显式判断，不适用部分说明原因，不因文档要短而删除关键边界。
- **风格（必须）**：明确可测，使用“当[条件]时，系统应[行为]，用户看到[结果]”；一条规则表达一个可检验要求。名称、状态、优先级和编号统一；不用“流畅、智能、适当、尽量、等等”代替规格。**建议**使用规则表、状态表和流程图，图中关键规则仍需可引用的文字说明。
- **缺失信息（必须）**：未知基线、阈值、负责人、日期、依赖承诺统一标“待确认”，说明确认路径、影响及是否阻塞实现或发布；确认方/期限未知也标待确认。缺数据时写测量或研究计划，不能猜数值、编造排期或把愿望写成承诺。关键规则未确认时不得声称可直接验收。
- **规范强度**：“必须”为底线；“建议”可按场景调整；“条件适用”须判断是否触发，不适用时说明原因。PRD 定义产品行为和约束，不展开工程实现取舍；相关实现链接 [技术方案 / 设计文档](../technical-design/README.md)，决策摘要链接 [One Pager](../one-pager/README.md)，不在此引入其写作约束。

## 二、整体结构与模板

章节按下列顺序组织，顺序固定；不适用的小节说明原因后省略，不删除整段证据链。

1. 文档信息与变更记录
2. 背景、问题与目标
3. 用户、场景与流程
4. 范围、需求清单与优先级
5. 功能规则与异常处理
6. 非功能要求与数据埋点
7. 验收标准与发布判定
8. 依赖、风险与开放问题
9. 里程碑与协作安排
10. 附录与来源

完整可复制模板见 [templates/prd.md](templates/prd.md)，内含空白模板、填写示例、真实示例链接。写作时先取模板，再回到本文「三、各部分写作要求」逐节核对；模板与本文小节一一对应。

## 三、各部分写作要求

### 1. 文档信息与变更记录

- **目的**：确定当前规格和范围变更的有效状态。
- **必须写什么**：标题、状态、版本、作者/评审方、更新日期、相关材料；变更记录说明增删改内容、原因、影响编号及确认状态。未知身份或日期待确认，已批准须有记录依据。
- **表达要求**：需求编号稳定且不复用；删除需求保留编号并标删除原因，不默默抹去历史。区分提议变更与已接受变更。
- **如何检查**：研发、设计和测试引用同一有效版本；变更记录能定位受影响条目与验收。
- **常见错误**：仅更新版本号；修改范围不留痕；被抄送的人自动变成评审通过者。

### 2. 背景、问题与目标

- **目的**：解释需求成立的理由和成功的定义。
- **必须写什么**：问题对象、现象、影响、证据与局限；预期结果、问题层面的非目标；目标编号、指标定义/单位、基线、目标条件、来源与窗口。缺基线写测量计划，缺目标写确认事项。
- **表达要求**：问题与解决方法分开；业务结果与交付完成分开。不要把相关性写成因果，也不要把预测收益写成已取得成果。
- **如何检查**：证据确实支持问题，指标能够回答是否改善，观察窗口足以解释判定；目标在第 7 节有对应验证。
- **常见错误**：“上线功能”是唯一成功条件；引用无样本信息的反馈；无依据填写增长百分比。

### 3. 用户、场景与流程

- **目的**：让需求落在真实使用条件上，建立规则适用的上下文。
- **必须写什么**：以下角色、场景、流程要素；未验证项必须与有证据场景区分。
- **表达要求**：角色由行为与权限定义，流程使用稳定状态名称；不使用虚构人物故事冒充研究结论。
- **如何检查**：每条主要需求能回溯到场景，主流程入口/终态清楚，角色权限与规则一致。
- **常见错误**：泛称“所有用户”；只贴流程图无条件；把内部希望当用户痛点。

#### 用户与场景

**必须**写角色、任务、触发条件、环境或权限限制、当前做法、痛点及期望结果；用场景编号关联需求与证据。**条件适用**：多角色协作时补各方交接与信息可见性。检查场景能否复现、证据覆盖何种用户；避免没有来源的“典型用户”与不影响规则的画像装饰。

#### 主流程与状态

**必须**写入口、前置条件、用户操作、系统反馈、关键分支、终态与可回退路径；有持续状态的功能需写状态、触发事件、转换条件和允许操作。图应链接到规则编号。检查同一事件在不同状态下的行为是否明确；避免只有成功路径或界面名而无状态含义。

### 4. 范围、需求清单与优先级

- **目的**：形成可引用的交付边界和排序依据。
- **必须写什么**：本期范围/非范围、唯一需求编号、场景/目标关联、行为摘要、优先级与理由、本期状态及验收索引。
- **表达要求**：需求摘要独立可读，一条需求不捆绑无关行为；范围与优先级分开，重要不等于本期承诺。
- **如何检查**：需求清单、详细规则和验收双向一致；没有无场景来源的功能；延后和删除项可区分。
- **常见错误**：所有需求都最高级；一句“优化体验”包含多个需求；以优先级暗示排期已承诺。

#### 范围与边界

**必须**说明包含/不包含的用户、入口、端或版本、数据对象和业务阶段中适用项，尤其说明容易误认为包含的相邻能力。**条件适用**：分期交付时逐期列边界，不把后期计划写成本期规则。检查非范围不与当前流程冲突；避免“其他后续支持”等无限范围。

#### 优先级与排序

**必须**先定义分级语义，再依据用户影响、目标贡献、风险、依赖和投入给理由；不得假定所有组织的 P0/P1 含义相同。**建议**区分发布必需项和可延后项；排序依赖未知时标待确认。检查最高级条目是否真是阻塞条件、冲突时取舍是否可解释；避免按提出者级别或无依据“紧急”排序。

### 5. 功能规则与异常处理

- **目的**：定义研发和测试无需猜测的产品行为。
- **必须写什么**：逐需求的前置条件、输入限制、操作、输出/反馈、权限、状态变化、默认值和异常规则；交互稿仅作为关联材料，不能替代业务逻辑。
- **表达要求**：规则以需求编号引用；条件与结果对应。参数边界未确定时明确待确认，不用“合理上限”掩盖缺失。
- **如何检查**：同一输入和状态下预期结果唯一，规则与界面/流程一致，权限及异常覆盖适用场景。
- **常见错误**：只有截图；使用“按现有逻辑”却不链接或描述；多个需求共享含糊规则。

#### 输入、输出与业务规则

**必须**说明字段含义、必填性、格式/长度/取值边界、默认值、校验时机、排序/计算规则及结果呈现；涉及业务对象时补创建、编辑、删除和权限限制中适用项。具体文案已确认时可引用，未确认时标待确认。检查边界值、重复输入和权限变化下的结果；避免以工程方案替代产品约束。

#### 异常、空态与恢复

**必须**判断并覆盖空数据、无结果、无权限、无网络、超时、服务失败、重复操作、部分成功和并发变化等适用情况；说明用户反馈、可继续操作、重试与恢复后的结果、已有数据是否保留。**条件适用**：不可逆操作需说明确认机制和误操作处置。检查每个异常分支有明确终态或恢复路径；避免一律“提示失败”或默认重试必然成功。

### 6. 非功能要求与数据埋点

- **目的**：补齐功能行为之外的可测约束和效果观测能力。
- **必须写什么**：适用非功能约束、测量条件与方法；指标/事件与目标关联、采集与数据处理规则；不适用项给原因。
- **表达要求**：写外部可验证的约束，不预设内部技术实现；区分产品目标、工程可行性待确认项和真实合规要求。
- **如何检查**：约束可测且可在验收定位，指标口径一致，采集字段有用途和合法处理依据。
- **常见错误**：堆“高性能高可用”；埋点只有事件名；为采集方便记录不必要的个人信息。

#### 非功能约束

**条件适用：涉及相关能力时必须**给性能的负载/统计分位/窗口、容量边界、兼容端与版本、权限与审计、隐私/保留/删除、可访问性及本地化要求。没有阈值则写待确认与确认方法。检查不同环境下的口径可比、约束来源明确；避免直接抄通用阈值或声称未经核实的合规达标。

#### 埋点与指标口径

**条件适用：需要量化效果或行为观测时必须**写事件标识、触发条件/时机、成功与失败口径、参数类型/含义、去重规则、用户/会话统计范围、排除项、关联目标、观察窗口及数据访问/保留规则。无采集需求时说明如何以其它证据验证。检查同一动作是否重复计数、漏采失败是否扭曲指标、基线与上线后口径是否一致；避免“埋点待研发补充”而没有统计定义。

### 7. 验收标准与发布判定

- **目的**：给需求是否完成和是否可发布提供可复现的判断。
- **必须写什么**：与需求、目标、约束关联的验收编号、前置条件、触发行为、预期结果与验证证据；发布必须通过项、已知限制及适用的业务停止/恢复条件。
- **表达要求**：使用“给定—当—则”，每条标准可独立执行；“则”写可观测结果及已确认边界。实现发布操作链接技术方案，不在此复制工程细节。
- **如何检查**：所有纳入需求和适用约束均有验收，负向场景及边界覆盖，未决阈值不被当已通过。
- **常见错误**：验收只是重写需求标题；用“产品满意”代替标准；功能通过但关键指标或权限无人验证。

#### 用例覆盖与判定

**必须**覆盖主路径、适用异常、权限差异、边界值、状态转换和跨版本情况；注明人工检查、自动测试、实验或数据分析方法。**条件适用**：长期效果无法发布前确认时，区分发布前合格条件与发布后效果评估，不虚构即时结论。检查测试数据和环境能复现条件、失败能定位编号；避免把不可测形容词当验收或以所有用例穷举替代关键规则。

### 8. 依赖、风险与开放问题

- **目的**：让未满足的前提和需要决策的事项可见。
- **必须写什么**：编号、依赖交付物/风险触发条件/开放问题、影响及阻塞阶段、完成或确认条件、责任方、时间与状态。期望交付时间与已确认承诺分开，未知均待确认。
- **表达要求**：问题可回答，依赖可验收，风险可采取措施；重大问题说明是否影响范围或发布。
- **如何检查**：规则中的待确认项在此可定位，关键阻塞有确认路径，依赖未到位时有明确范围处理。
- **常见错误**：依赖方只是团队名无交付物；无依据指派负责人；未决规则默认为研发自由决定。

### 9. 里程碑与协作安排

- **目的**：明确阶段性对齐和交付判定，不制造未经确认的排期。
- **必须写什么**：阶段范围、交付物、前置条件、责任/验收方、时间与确认状态、完成条件；适用时包括研究、设计、联调、验收及发布后观察。
- **表达要求**：初步建议、估算与已承诺计划分开；未确认日期和人员待确认。**建议**按可验证交付物划分，而非只有会议名称。
- **如何检查**：里程碑覆盖本期范围，依赖顺序合理，验收方和完成条件明确或标明待确认。
- **常见错误**：先填上线日再忽略依赖；只排开发；“完成评审”没有通过条件。

### 10. 附录与来源

- **目的**：保留证据与补充材料，并让正文保持可用。
- **必须写什么**：正文引用的研究、数据、设计材料、术语等索引，说明用途、版本/时间和对应编号；必要时交代证据局限。
- **表达要求**：正文写规则与结论，附录提供细节；具体示例若非真实证据必须明确标“虚构格式示例”。不复制敏感原始用户数据。
- **如何检查**：链接有效且版本正确，设计稿与规则相符，读者无需翻遍附件才能知道验收条件。
- **常见错误**：未标版本的设计稿；链接代替规则；虚构示例被写成用户事实。

## 四、交付前检查

- [ ] 模板所有编号部分齐全，头部信息与变更记录有效，不适用项有理由。
- [ ] 问题和场景有证据或待验证标记；目标、需求、规则与验收可双向追溯。
- [ ] 本期范围和非范围明确，优先级定义与理由完整，删除编号未复用。
- [ ] 条件、状态、字段、默认值、权限、异常与恢复不存在相互矛盾或隐含规则。
- [ ] 功能、非功能约束和埋点均完成适用性判断；统计口径与验收可测、可复现。
- [ ] 未编造用户事实、指标、负责人、日期或依赖承诺；待确认项注明影响和阻塞阶段。
- [ ] PRD 保持产品行为规格，不以实现细节、设计截图或附件替代核心规则。
- [ ] Markdown 围栏成对、表格可读、链接目标正确，术语和版本一致，无敏感信息泄露。
