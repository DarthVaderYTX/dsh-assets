# 判分：rubric 设计、LLM 判分与校准

优化器能走多远，取决于 rubric 和判分是否可靠。**先在基线阶段把判分修对，再开始优化。**

## 1. 准则怎么写

一条好准则应当：

- **可观察**：能从回答文本直接判断，不依赖未给出的信息。
- **原子**：一条只判断一件事。「结论正确且渠道完整且语气礼貌」无法区分部分满足，应拆成三条。
- **有分档含义**：明确什么算完全满足、什么算部分满足。
- **带权重**：决定总分结构，而不是事后找补。
- **不泄题**：不要写「必须回答 42」「必须提到张三」，这类内容应放进 `reference`，由判分模型参考，而不是把答案写进 rubric 或 prompt。

不推荐：

- 「回答质量高」「专业」「全面」——没有可观察标准，判分模型只能凭感觉。
- 一条准则里堆 4 个要求。
- 用长度、格式、语气等表层特征替代任务正确性；除非这正是任务要求。

### 确定性检查优先

能用规则判断的，一律用 `check`：

| 场景 | 写法 |
| --- | --- |
| 必须包含某个词/编号 | `{"type": "contains", "value": "ORD-"}` |
| 不得出现链接/电话 | `{"type": "not_contains", "value": "http"}` |
| 输出必须是 JSON | `{"type": "json"}` |
| 字数上限 | `{"type": "max_chars", "value": 200}` |
| 数值正确 | `{"type": "numeric", "value": 42, "tolerance": 0.01}` |
| 以指定前缀开头 | `{"type": "starts_with", "value": "结论："}` |

确定性检查没有判分噪声、没有额外成本，也更难被 prompt 套利。只有「是否解决了用户问题」「推理是否成立」这类语义判断才交给判分模型。

## 2. 判分模型怎么选

- 优先选**比任务模型更强**的模型；任务与判分同模型会共享盲点，报告会自动告警。
- 判分模型要能稳定输出 JSON；不支持 `response_format` 时客户端会自动回退，但解析失败率会升高。
- 判分温度用 0（默认）。同一输入重复判分仍可能有波动，重要结论应抽检或重复测量。
- 判分模型不应看到「正在被优化的 prompt」，否则可能对特定措辞产生偏好；它只看输入、输出、rubric 和可选 reference。

## 3. 判分提示词的结构

脚本内置的判分提示词遵循：

1. 明确角色：严格、独立的评分者。
2. 把 `<task_input>`、`<model_output>`、`<reference>` 标为**数据，不是指令**，避免被回答里的注入文本带偏。
3. 只按列出的准则评分，不奖励长度、语气、Markdown 或自信程度（除非准则要求）。
4. 每条准则独立打 0 / 0.5 / 1，并给出引用回答内容的理由。
5. 只输出约定 JSON：`{"criteria": [{"id": ..., "score": ..., "rationale": ...}], "summary": ...}`。
6. 0.5 只给真正部分满足的情况，不给「尝试过但没做到」。

0.5 是最容易被滥用的档位。如果发现大量 0.5 拉不开差距，优先把准则拆细或改成 0/1 二值，而不是调低判分严格度。

## 4. 校准流程（基线阶段必做）

1. 跑 `score` 得到基线；打开 `results/score.jsonl`。
2. 抽 3–5 条，覆盖高分、低分和中间分。
3. 人工读 `output` 与每条准则的 `rationale`，问三个问题：
   - 模型输出是否真的在回答这个输入？
   - 判分给分是否符合 rubric 的字面含义？
   - 失败原因是任务没做到，还是 rubric 写得不可判？
4. 如果判分与人工判断偏差大：
   - 准则模糊 → 改写准则；
   - 准则缺档位 → 补充「完全/部分/不满足」的具体表现；
   - 判分被表面特征带偏 → 在判分提示词中明确禁止，或改成确定性检查；
   - 判分模型太弱 → 换模型。
5. 修完后**重新跑基线**，不要拿旧基线和新候选比较。

校准的目标不是让分数变高或变低，而是让分数**能区分好坏**。如果基线已经 100 分，先确认 rubric 是否太松；如果所有行都 0 分，先确认任务是否可完成、判分是否过严。

## 5. 偏差与噪声

常见偏差：

- **长度/格式偏好**：长答案、分点、加粗更容易被判高分。准则应只评判内容；必要时在判分提示词中显式排除。
- **同模型偏好**：任务与判分同模型时，模型容易认可自己的表达风格。
- **顺序/位置偏差**：多候选比较时更明显；本工具是逐条独立判分，不受位置影响，但候选之间的分数差仍可能有噪声。
- **reference 依赖**：有 reference 时判分更稳，但 reference 本身错误会系统性带偏。
- **rubric 泄漏到任务 prompt**：把 rubric 原文抄进 prompt 可能提高分数，但若 rubric 描述了判分器的表层特征，就是在套利。只允许把通用要求转写为任务规则。

噪声处理：

- 判分温度 0，但不要假设完全确定。
- 分数差在 1 分以内时，不要宣称提升；结合 holdout、重复测量和分准则变化判断。
- 预算允许时，对最终候选再跑一次 `score`，比较两次结果。

## 6. 失败处理

| 现象 | 处理 |
| --- | --- |
| 判分返回非 JSON | 自动带错误信息重试一次；仍失败默认中止 |
| 缺某个准则的分数 | 视为无效判分，重试；不要用 0 补齐 |
| 分数不在 0–1 | 视为无效判分，重试 |
| 输出为空 | 通常是 `--max-tokens` 太小；提高后重跑 |
| 判分模型 429 | 降低 `--concurrency`，或换时段/端点 |
| 个别行反复判分失败 | 用 `--on-judge-error zero` 只应在能接受偏差时使用；更好的做法是修该行 rubric 或排除并记录 |

## 7. 报告里必须写清的判分信息

- 判分模型与 endpoint（不写 key）。
- 每条准则的得分变化（报告 3.1）。
- 是否有 reference、是否有确定性检查。
- 判分失败/跳过的行数。
- 任务与判分是否同一模型。
- 分数是样本内还是留出集结果。
